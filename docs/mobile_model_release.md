# Мобильный выпуск MobileNetV3-Small

## Текущий вариант по запросу пользователя: без порога

Подготовлен отдельный выпуск `poi-small-2026-10-30-argmax-v2` в
`.runtime/mobile_argmax_v2/public/`, архив —
`.runtime/mobile_argmax_v2/poi-small-2026-10-30-argmax-v2.zip`.
Веса FP32 и порядок классов сохранены; изменена только политика решения.
Строгий предыдущий выпуск не перезаписан.

В новой `decision_policy.json`:

```json
{"mode": "argmax_only", "confidence_rejection_enabled": false, "threshold": 0.0}
```

Для этого режима Flutter-разработчик убирает условие по score, сохраняя проверку
`predicted_class_index == target_class_index` и поддержку целевого POI.
Порог 0.0 оставлен для совместимости с прежней проверкой `score >= threshold`;
не следует заменять его старым встроенным порогом. Применяются policy и mapping
из этого же выпуска. Приложение c61 здесь не изменялось: разработчик должен
подключить новый пакет и эту логику на своей стороне.

На 185 известных тестовых фото это даёт 156 правильных распознаваний (84.32%)
и 29 неверных. Это не улучшение классификатора: отключён дополнительный отказ.
Каждое постороннее фото также получает одну из 23 меток. Доля принятия внешних
негативов как **любой** известный класс становится 100%; частота ложного
подтверждения конкретного целевого POI зависит от цели и отдельно не измерена.
Неизвестные цели, ошибки декодирования и невалидные logits по-прежнему отклоняются.
Проверки SDK-ID и реальные Android-тесты остаются обязательными для интеграции.

Воспроизводимая пересборка в новом каталоге:

```powershell
.\.venv\Scripts\python.exe scripts/package_mobile_no_threshold.py --output .runtime/mobile_argmax_repeat
```

Ниже описан исходный экспорт и строгая политика предыдущего выпуска;
условие `score >= threshold` относится к режиму `threshold`, а не к `argmax_only`.

## 1. Запуск конвертации

Из корня проекта с работающим Docker Desktop (Linux containers):

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run_mobile_export.ps1
```

Первый запуск собирает отдельную Linux CPU-среду и скачивает библиотеки.
Фото, разметка и веса остаются на компьютере; сетевые операции нужны для образа
и библиотек. Build-context содержит только Dockerfile и requirements.
Код и подготовленные массивы передаются через `docker cp` в локальный named volume.
Bind mount диска I: не используется. Обучение не запускается.

Входы уже подготовлены в `.runtime/mobile_export_v1`. Для нового независимого
запуска можно собрать их заново в другом каталоге:

```powershell
.\.venv\Scripts\python.exe scripts/prepare_mobile_export.py --output .runtime/mobile_export_v2
powershell -ExecutionPolicy Bypass -File .\scripts\run_mobile_export.ps1 -Work .runtime/mobile_export_v2 -Output .runtime/mobile_export_result_v2
```

Существующие каталоги не перезаписываются. При сбое смотрите
`.runtime/mobile_export_result_v1/status.json`. Контейнер и volume сохраняются
для диагностики; их имена выводятся скриптом. Не запускайте одновременно два
экспорта с одним выходным каталогом.

### Повторная оценка после ошибки XNNPACK

Первый запуск сохранил оба TFLite-файла. Чтобы использовать их повторно и
оценить INT8 на CPU без XNNPACK при сбое ускорителя:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run_mobile_export.ps1 -Output .runtime/mobile_export_result_v3 -ReuseModels .runtime/mobile_export_result_v1
```

Модели не конвертируются и не квантуются повторно. Проверяются входные SHA-256,
валидированный FP32-пакет и формат сохранённых моделей; хеши повторно используемых
файлов записываются в новый отчёт. Качество, порог и контрольные ответы
рассчитываются заново. Старый результат сохраняется. Ошибки, не связанные
с XNNPACK, не скрываются. Выбранный runtime записывается в tensor_contract
и manifest; успешная CPU-оценка не означает совместимость с XNNPACK на Android.
Launcher сохранён с UTF-8 BOM для корректных русских сообщений в Windows PowerShell 5.1.

Скрипт фиксирует версии в `environment.json`, `pip-freeze.txt` и ID образа
в `docker-image-id.txt`. Верхние зависимости закреплены, но транзитивные
зависимости и базовый образ до первой успешной сборки не являются полным lock.
Для точного повторения используйте сохранённый Docker image ID локально
и сохраните образ вместе с приватными рабочими материалами.

## 2. Что проверяется до упаковки

| Проверка | Правило |
|---|---|
| Источник | SHA-256 checkpoint совпадает с утверждённым обучением |
| Данные | SHA-256 всех подготовленных входов; проверенные метки; отсутствие пересечений групп между split |
| FP32 | Максимальная ошибка logits ≤0.001 и 100% совпадение top-1 с PyTorch на всех контрольных кадрах |
| INT8 | Есть int8-тензоры; файл меньше FP32; падение Accuracy и Macro-F1 на val не более 1 процентного пункта |
| Отказ | Порог каждого варианта выбран только по negative_val для FPR≤1%, с учётом совпадающих score |
| Test | Только диагностика после фиксации решений; не выбирает квантование или порог |
| Пакет | Разрешённый список файлов, согласованность классов и 2GIS, SHA-256 и размеры |

INT8 здесь означает статическое квантование поддержанных операций. Вход и выход
могут иметь float32, int8 или uint8: фактические dtype, scale и zero_point записываются
в preprocessing.json. Возможны оставшиеся float-операции. Скрипт сообщает число
float32/int8 тензоров и **не заявляет**, что граф целиком целочисленный или готов
к NPU. Размер и скорость нужно измерить на телефоне.

В `comparison.json` сохраняются Accuracy, Macro-F1, число FP и FPR
на внешних негативах, ошибочные подтверждения и true accept rate.
False Positive внешнего негатива и ошибка между двумя известными POI — разные
случаи; они учитываются отдельно. Старый test уже использовался, поэтому
потребуется новый независимый набор телефонных фото для продуктовой оценки.

Текущий Python baseline: test Accuracy=84.32%, Macro-F1=82.51%,
external FPR=2/573≈0.35%. Проверенный FP32 TFLite: Accuracy=84.32%,
Macro-F1=82.51%, external FPR=1/573≈0.17%, true accept=22/185≈11.89%.
Порог FP32 был заново выбран по negative_val; это другой рабочий порог,
поэтому изменение FPR не доказывает улучшение распознавания.
Строгий старый порог сильно ограничивает подтверждение правильных фото;
конвертация сама по себе эту проблему не решает.

## 3. Контракт для Flutter-разработчика

- Логический вход `[1,224,224,3]`, порядок **RGB**, значения 0…255, NHWC.
  Физический dtype брать из preprocessing.json. Для float32 достаточно cast;
  для int8/uint8: `q=clip(round(rgb/scale+zero_point), min_dtype, max_dtype)`,
  половины округлять от нуля. Использовать параметры входного тензора,
  не интерпретировать RGB-байты как signed int8 напрямую.
- Применить EXIF-ориентацию; убрать alpha через согласованное RGB-преобразование.
  Эталонный Python-декодер делает JPEG draft640, уменьшение в рамку320 без
  увеличения через LANCZOS, затем центрированный ImageOps.pad224 через BILINEAR
  с цветом `(124,116,104)`. Нельзя растягивать фото до квадрата.
- Нормализация ImageNet встроена в модель: во Flutter не делить повторно на255
  и не вычитать средние. Отличия мобильного декодера и resize обязательно
  проверить на согласованных фото с EXIF и разными пропорциями.
- Выход `[1,23]` — logits. Целочисленный выход сначала деквантовать:
  `logit=(q-zero_point)*scale` с параметрами выходного тензора.
  Затем один раз применить стабильный softmax в Dart double:
  вычесть максимум, взять exp, разделить на сумму.
- Это POI-классификатор. Для `poi_search` подтвердить задание только если
  целевой POI поддерживается, top-1 совпадает с его class_index и
  max-softmax ≥ threshold из **того же** выпуска. Иначе отказ/повторный кадр.
  Score не является калиброванной вероятностью правильности.
- Не заменять существующую механику `class_search` (арки, колонны и т.п.)
  этой моделью: у неё другой набор классов.
- SDK-ID 2GIS хранить строками, порядок class_index не менять.
  `main_entrance` пока не имеет подтверждённого SDK-ID: кандидат относится ко всему
  парку. Остальные соответствия тоже требуют проверки в SDK разработчиком.
- В `conformance.json` есть пять синтетических RGB-входов с ожидаемыми logits:
  они позволяют проверить порядок каналов, нормализацию и вызов runtime без фото.
  Это отдельная проверка от декодирования JPEG и качества распознавания.

Изменений в c61 не сделано. Разработчику потребуется выбрать совместимый
LiteRT/TFLite runtime, проверить minSdk и поддержку операций, запускать inference
вне UI isolate, обработать неподдерживаемые цели и ошибку загрузки модели.
Сначала проверить CPU, затем отдельно сравнить делегаты на реальном устройстве.
Для iOS потребуется отдельная сборка и проверка на устройстве.

## 4. Что положить на хостинг

**Только содержимое** `.runtime/mobile_export_result_v3/public/`.
В индекс включён только прошедший проверки FP32. INT8 отклонён и не публикуется.
FP32 ещё требует измерений скорости и проверки на Android.

```text
release_index.json
poi-small-2026-10-30-v1/
  fp32/
    model.tflite
    class_mapping.json
    poi_2gis_mapping.json
    preprocessing.json
    decision_policy.json
    conformance.json
    manifest.json
```

Проверка готового варианта перед загрузкой:

```powershell
.\.venv\Scripts\python.exe scripts/check_mobile_release.py .runtime/mobile_export_result_v3/public/poi-small-2026-10-30-v1/fp32
```

Используйте статический HTTPS-хостинг. Сохраняйте путь с версией неизменяемым:
новая модель или policy — новый выпуск. `release_index.json` содержит только
прошедшие проверки варианты и не разрешает автоматическую активацию. Для versioned файлов можно
использовать длительный cache-control immutable, для индекса — revalidation.
`model.tflite` отдавать как application/octet-stream, JSON — application/json.
Не публикуйте `.runtime` целиком, model.pt, массивы входов, CSV с атрибуцией,
фотографии, Python-среду или приватные контрольные результаты.

Разработчик скачивает пакет, сверяет хеш манифеста из доверенного индекса и хеши
всех файлов, затем атомарно активирует всю версию. Нельзя смешивать model/mapping/
policy разных выпусков. SHA-256 обнаруживает повреждение, но сам по себе
не заменяет доверенный канал обновления. При ошибке сохраняется предыдущая
рабочая версия. Для offline с первого запуска начальный пакет лучше включить
в assets приложения; хостинг нужен для обновлений.

## 5. Что осталось перед включением для пользователей

1. Получить успешный `status.json` и проверить `comparison.json` FP32/INT8.
2. Вместе с разработчиком проверить реальный Android: top-1/score,
   latency p50/p95, время загрузки, RAM, размер APK и работу без сети.
3. Проверить SDK-ID каждого POI; исправить связь арки главного входа.
4. Проверить вертикальные/горизонтальные фото, EXIF, тёмные и чужие объекты,
   несколько POI в кадре, неизвестные POI, ошибки загрузки и обновления.
5. Утвердить продуктовый компромисс между ошибочными подтверждениями и отказами
   на новом телефонном наборе, сохраняя отдельный финальный test.
6. После приёмки разместить public-пакет на выбранном хостинге и передать URL
   разработчику. Автоматической публикации здесь нет.
